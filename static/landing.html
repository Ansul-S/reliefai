What it actually does

Not a chatbot with a database attached

It picks its own tools

The orchestrator runs a real function-calling loop against twenty-one tools served over MCP — supply levels, volunteer availability, shift gaps, tasks, notes, broadcasts — and a live weather forecast, the one tool that reads from outside the operation's own database. Nothing is hard-coded to a command; the model decides what to call and when it has enough to answer.

It writes to the operation

Scheduling a shift creates a shift. Filing a procurement task creates a task. Sending a broadcast translates it into six languages and records it. The loop is bounded, duplicate calls are refused, and every call lands in a trace you can read back.

It is graded on the numbers it states

A twelve-case golden dataset scores every run on five dimensions — tool selection, grounding, side effects, loop health, and an LLM judge. The grounding scorer checks each figure in the answer against what the tools actually returned, so an invented stock level fails even when the prose reads well.

The loop

  1. 01Read the command. A coordinator describes what happened, in their own words.
  2. 02Choose a tool. The model calls one of twenty-one, with arguments it composed itself.
  3. 03Look at the result. Real rows come back from the operation database.
  4. 04Decide again. Call another tool, or stop — bounded, with repeats refused.
  5. 05Answer from the data. Summary, alerts, and next actions, traceable to the calls that produced them.
